=== WHY THIS VERSION EXISTS ===

The old workflow was: run game → crash → read 1 error log → fix only those
files → repeat. This means each round only ever fixes whatever Minecraft
happened to hit first. Every round looks "complete" but the game finds new
crashes next time because nobody ever checked the OTHER 95% of the datapack
that just didn't get loaded yet.

This version instead validates the ENTIRE datapack proactively, using known
26.1.2 breaking-change patterns — not just whatever the latest error log says.
The error log (if provided) is used as a confirmation/priority signal, not
the only source of truth.

=== STEP 1 — BUILD THE KNOWN BREAKING-CHANGE CHECKLIST ===

Before scanning any files, confirm this checklist by cross-referencing
./26.1.2/data/minecraft/worldgen/ schemas. This is the full list of every
breaking change identified across all previous rounds. Do not skip any item
even if you believe it was "already fixed" — verify, don't assume.

  [ ] dirt_provider / force_dirt — removed from TreeFeatureConfig
  [ ] Missing "type" field — required at top level of configured_feature
      AND placed_feature files
  [ ] minecraft:random_patch — no longer a valid feature type; must be
      unwrapped into separate configured_feature + placed_feature pair,
      OR the feature reference corrected to point at the real 26.1.2
      placed_feature ID
  [ ] waterlogged / persistent / distance — removed from inline blockstate
      providers
  [ ] exclusion_radius_xz / exclusion_radius_y / required_empty_blocks —
      removed from ColumnPlacer (verify per-feature-type before deleting;
      some placer types may still use similar keys)
  [ ] baby_assets / baby_asset_id — now required in wolf_variant /
      chicken_variant files
  [ ] extra_branch_steps / extra_branch_length /
      place_branch_per_log_probability / can_grow_through — removed from
      FoliagePlacer (verify per-feature-type; some types may still require
      can_grow_through)
  [ ] Numeric range violations — IntProvider/y_spread/xz_spread values must
      fall within ±16 (not ±20 or other out-of-range values used pre-26.1.2)
  [ ] Missing "blocks" key — required in certain placed_feature configs
      (e.g. solid_clouds-style features)
  [ ] Missing "y_spread" — required in random_offset placement modifiers
  [ ] FEATURE ↔ BLOCK CONFUSION (recurring, highest-priority check):
      A feature ID (minecraft:patch_large_fern, minecraft:patch_sugar_cane,
      minecraft:patch_waterlily, minecraft:patch_firefly_bush*, etc.) is
      ONLY valid in:
        - a biome's "features" list
        - a placed_feature's top-level "feature" field
      NEVER valid in:

        - "blocks" lists or block-matching predicates
        - blockstate "Name" fields

      (patch_large_fern → large_fern, patch_sugar_cane → sugar_cane, etc.)
  [ ] Unbound registry values — any placed_feature or configured_feature
      referenced by a biome/feature file but missing its own JSON definition
      (check if the file needs to be copied from ./26.1.2/ or restored from
      ./WWOO_ORIGINAL/)
  [ ] Unknown/removed keys not listed above — heightmap, dusted, predicate,
      snowy, creaking, sapling_provider — verify against ./26.1.2/ per file

=== STEP 2 — RUN THE AUTOMATED SCANNER ===

Run the scanner script instead of manually walking the file tree:

  python3 wwoo_schema_scan_v2.py --out sweep_[N]_scan

This produces sweep_[N]_scan.json and sweep_[N]_scan.md, covering every
checklist item from Step 1 except "minecraft:random_patch unwrapping"
(the scanner flags random_patch as a "type" value, but the actual unwrap
logic still requires manual judgement per Step 3).

Read sweep_[N]_scan.md in full. Do NOT trust category_counts alone —
open issues_by_file in the .json and spot-check at least 3 files per
category before treating the count as ground truth. The scanner does
context-aware checks for known false-positive patterns (predicate inside
block_predicate_filter, exclusion_radius/can_grow_through inside mangrove
root placement) but it is not infallible — if a flagged key looks like it
might be valid in its context, verify against ./26.1.2/ before treating
it as a real issue rather than assuming the scanner is right.

Print the complete scan summary before fixing anything:
  "Scanner run complete. X total issues found across Y files.
   Breakdown: [checklist item]: [count] files, ...
   [Z] unbound references found."

DO NOT begin fixing until this full summary is printed AND you have
spot-checked the categories with the highest counts.
