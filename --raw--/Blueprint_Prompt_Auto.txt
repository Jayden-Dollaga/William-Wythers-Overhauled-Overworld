=== STEP 2 — LOOK UP EACH ERROR IN ./26.1.2/ ===

For EVERY remaining error found in Step 1:
  1. Find the equivalent file in ./26.1.2/data/minecraft/worldgen/
  2. Check what the correct value/key/type should be
  3. Only proceed if you find a 100% confirmed match

If you cannot find the answer in ./26.1.2/ → mark ⚠️ UNCERTAIN and skip.
NEVER guess. NEVER use memory. ALWAYS check ./26.1.2/ first.

Common lookups:
  "Unbound values in placed_feature: minecraft:X"
    → check if minecraft:X exists in ./26.1.2/data/minecraft/worldgen/placed_feature/
    → if not, find the new name by searching ./26.1.2/data/minecraft/worldgen/placed_feature/
    → then find which datapack file references the old name and update it

  "Unbound values in configured_feature: minecraft:X"
    → same but check ./26.1.2/data/minecraft/worldgen/configured_feature/

  "No key Y in MapLike"
    → find a vanilla file of the same feature type in ./26.1.2/ and check if Y is required
    → if Y is missing from vanilla → add it with the value from vanilla
    → if Y doesn't exist in vanilla schema → the key was removed, delete it

  "Unknown key Y"
    → key was removed in 26.1.2, delete it

  "Failed to parse"
    → open the file and check for JSON syntax errors or invalid values

FEATURE ↔ BLOCK CONFUSION CHECK (recurring bug pattern — always check this):
  A feature ID (e.g. minecraft:patch_large_fern, minecraft:patch_sugar_cane,
  minecraft:patch_waterlily) is only valid in:
    - a biome's "features" list
    - a placed_feature's top-level "feature" field
  It is NEVER valid inside:
    - a block tag (tags/block/, tags/blocks/)
    - a "blocks" list or block-matching predicate
    - a blockstate "Name" field
  If a patch_* feature ID appears in any of those wrong contexts, replace it
  with the corresponding real block ID (e.g. patch_large_fern → large_fern,
  patch_sugar_cane → sugar_cane) instead of deleting it.
